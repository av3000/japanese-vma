# PDF fonts

> **Nothing in the application references `HanaMinA-subset.ttf`.** All three PDF layouts still
> load `/usr/share/fonts/truetype/hanazono/HanaMinA.ttf` from the image. This directory is kept
> pending the decision in **[#329](https://github.com/av3000/japanese-vma/issues/329)** — delete
> it, or adopt it as the fix for [#317](https://github.com/av3000/japanese-vma/issues/317). Read
> that issue before building anything on top of these files.

## What is here

| file | what it is |
| --- | --- |
| `character-set.txt` | Every character the PDF exports can render, one per line, sorted by code point. Generated by `php artisan pdf:extract-font-character-set`. |
| `HanaMinA-subset.ttf` | **Not committed** - build output, regenerate with `subset-font.sh`. HanaMinA cut down to exactly those 13,486 characters: 22.7 MB / 41k glyphs → 6.1 MB / 13.5k glyphs, with zero characters uncovered. |
| `subset-font.sh` | Rebuilds the subset from the system-installed HanaMinA and `character-set.txt`. |

## Why it exists, and why it is not wired up

It was built while diagnosing ~170 s kanji and word PDF exports, on the theory that Dompdf's
per-request font subsetting was the bottleneck and that a smaller source font would fix it.

That theory was wrong. The cost was never the font's glyph count — it was that Dompdf's font
cache (`storage/fonts`) sat on the `./:/var/www/html` bind mount. php-font-lib does about four
`seek`/`read` syscalls per glyph when it parses a font, and over Docker Desktop's Windows file
sharing each one costs roughly a millisecond. Parsing the `glyf` table of the *same file* took
**30.56 s from the bind mount and 0.07 s from container-local `/tmp`**.

The fix that shipped is the container-local anonymous volume for `/var/www/html/storage/fonts`
in `docker-compose.yml`. With it, exports run in ~5 s, and the original 22.7 MB font and this
6.1 MB subset perform identically (5.1 s vs 5.5 s). The subset buys nothing on speed.

What it might still be good for is **[#317](https://github.com/av3000/japanese-vma/issues/317)**:
`.docker/Dockerfile.ci` installs only `fonts-noto-cjk`, so neither HanaMinA nor IPAGothic exists
in the production image and those PDFs lose their Japanese text. A font committed here and loaded
via `resource_path()` resolves in every image by construction, instead of the Blade layouts'
`@font-face` paths having to stay in sync with each Dockerfile's apt list.

## Regenerating

Both steps are deliberately out of the app image — they run at most a couple of times a year,
whenever the dictionary import brings in characters the current subset does not cover.

```bash
docker exec laravel_app php artisan pdf:extract-font-character-set
```

That queries every column that can hold Japanese text (kanji, word and radical banks, tatoeba
sentences, article bodies), unions it with a fixed baseline of kana, Japanese punctuation and
Latin, and rewrites `character-set.txt`. One character per line means a new character shows up
as a single added line in review.

```bash
sh resources/fonts/subset-font.sh
```

That pulls HanaMinA out of the running container, runs `pyftsubset` in a throwaway
`python:3.12-slim`, and fails if any wanted character is missing from the result.

## If you wire it up

Change the `@font-face` `src` in all three layouts — `pdf/kanjis/mainlayout.blade.php`,
`pdf/articles/layout.blade.php`, `pdf/catalogues/layout.blade.php` — from the `/usr/share/fonts`
path to:

```blade
src: url('{{ resource_path('fonts/HanaMinA-subset.ttf') }}') format('truetype');
```

`config/dompdf.php`'s chroot already covers this: it whitelists `realpath(base_path())`. Leave
`enable_font_subsetting => true` — Dompdf still needs to embed only the glyphs each document
uses, and the rendered PDFs stay around 190 KB either way. IPAGothic has the same
production-image problem and would need the same treatment.
